## Findings

Ranked from most to least severe.

1. **F1 - the hidden modal test fails a faithful implementation, and the map tells only one bench arm how to pass it** (C8/C9). `telas.test.jsx:52` - `expect(id('fornecedor')).toBeNull()` before the click. The prototype keeps the modal in the DOM all the time and hides it with CSS (`contas.html:22`, `estilo.css:107-108`). The prompt (`task.json`) says to keep "os id e a navegação do protótipo". A faithful port that keeps the modal mounted and toggles `className={nova ? 'modal aberto' : 'modal'}` therefore fails this test for a reason the prompt never states. The React map prescribes exactly the shape that passes (`references/codigo-react.md:29`, `{aberto && <div className="modal aberto">}`), and only the `proto-codigo` arm reads it. That tilts C9 toward the new step.
2. **F2 - `escopo()` leaks `:root` out of the scope, and drops the font, when `tema.css` starts with `@import`** (C10 precision gap, AC 10 defect). `render.mjs:466` copies an `@`-headed chunk verbatim up to the next `}`. A statement at-rule has no `{`, so `@import url(...);\n:root{--cor:...}` becomes one head starting with `@` and is emitted unscoped. Reproduced: the output keeps `:root{--cor:#0f766e;--fonte:"Inter",sans-serif}` global. Because tema is concatenated after estilo (`:532`), the `@import` also lands after other rules, so browsers ignore it and the font never loads. `@layer x;` and `@charset` behave the same way (reproduced with `@layer base;\n.a{...}`: `.a` stays unscoped). This is a realistic input: the SKILL puts the project's font in `tema.css` (SKILL.md:29-34). C10 never feeds `tema.css` or any statement at-rule into `escopo` (`test:44`), and the "tipos de regra no escopo (4)" coverage row leaves this member out.
3. **F3 - the hidden tests cannot see the visual, and one of them depends on the space character** (C8/C9). (a) No assertion looks at classes, the `.prototipo` container or the CSS import. A naive implementation that ignores the prototype's look but copies its texts and ids passes 7/7. So C9 measures cost per pass of a text/id/navigation port, not "o mesmo visual". That gives the `toolkit` arm room to skip styling and look cheaper, which works against the step. (b) `telas.test.jsx:39` - `expect(rodape?.textContent).toContain('R$ 2.247,80')` compares raw `textContent` with an ASCII space. `toLocaleString('pt-BR', {style:'currency'})`, the natural way to format the cents in `dados.js`, emits U+00A0 after `R$`. The solution only passes because of `.replace(/ /g, ' ')` (NBSP to space) at `solution/src/telas/Contas.jsx:5`. The tbody checks (`:30-32`) use `getByText`, whose default normalizer folds NBSP, so they don't have this problem. Only the tfoot does.
4. **F4 - the bench cache is shared and writable through the junction** (bench/run.mjs). `linkDeps` (`bench/run.mjs:101-111`) links the workspace's `node_modules` to `bench/.cache/deps-<task>-<hash>/node_modules`. Anything the agent under test runs there (`npm install x`, `npm ci`) changes the dependencies that later arms and reps see. Vitest already writes its results cache through the link: after the dry run, `bench/.cache/deps-proto-react-*/node_modules/.vite/vitest` exists. Also, `:105` reuses any `node_modules` folder that exists, so an `npm ci` killed halfway (not a nonzero exit) leaves a partial cache that is reused forever. Deletion itself is safe (answer to (d)): on Node v24.21.0, `lstat` reports the junction as a symlink and `unlinkSync` removes only the link (`:117`). Separately, `rmSync` over a workspace that still holds the junction also left the target intact (tested with a temporary junction: the cache file survived both paths). Note that `:117`'s `catch` also swallows an `unlinkSync` failure and falls through to `rmSync`. That is safe on this Node version, but only because of `rmSync`'s behavior.
5. **F5 - Flutter `ThemeData`** (answer to (b), with no SDK to compile against). The generated code is valid as far as the Flutter docs go: `ColorScheme.fromSeed` accepts `primary`, `onPrimary`, `surface`, `onSurface`, `error` and, since the Flutter 3.22 colour-role change, `surfaceContainerLowest`. `ThemeData(useMaterial3:, colorScheme:, scaffoldBackgroundColor:, fontFamily:)` is valid, and so are `const double raioPrototipo = 8;` and a top-level `final`. Caveats: (i) this needs Flutter >= 3.22, and older SDKs fail to compile on `surfaceContainerLowest`; (ii) mapping `--fundo` (#f4f6f9, darker than surface) to `surfaceContainerLowest`, which M3 defines as the lightest container, is semantically inverted, so a widget that uses that role gets the background grey instead of the lightest tone; (iii) `fontFamily: 'Inter'` is written with no asset or `google_fonts` step, and neither `codigo-flutter.md` nor the notice tells the user to register the font, so Flutter silently falls back. Unsupported colours (for example `hsl(...)`) fail cleanly before anything is written.
6. **F6 - CSS scoping otherwise holds** (answer to (a)). Every rule in the shipped `estilo.css` comes out under `.prototipo` (C10's walk). `.entrada` and `.mobile` are plain classes in `estilo.css:124,128,141-142` (there is no `body.entrada`), so they become `.prototipo .entrada` / `.prototipo .mobile .btn`. They work when nested as a child div, which is exactly what the maps prescribe (`codigo-react.md:7-8,31-32`, `codigo-angular.md:7-8,31-32`). A single element `class="prototipo mobile"` would not match. `.modal.aberto` becomes `.prototipo .modal:target,.prototipo .modal.aberto` (reproduced) and works while the modal is rendered inside the container. A portal (React `createPortal`, MUI Dialog, Angular CDK overlay) would lose both the rules and the variables, and no map mentions it. Minor: `html,body{margin:0}` lands on the container (harmless), and `angular.json`'s `test` target `styles` is not updated (Karma tests run without the CSS). A brace inside a string (`content:"}"`) breaks the scoper. That is acknowledged by the `shortcut:` comment at `render.mjs:443` and absent from `estilo.css`.
